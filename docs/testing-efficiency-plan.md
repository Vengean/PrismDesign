# Prism Studio 测试准确性与执行效率优化方案

## 1. 背景

当前 Prism Studio 的自动测试由 Agent 驱动浏览器完成。一次测试通常包含测试用例定义、浏览器连接、页面观察、点击与输入、等待页面变化、截图、运行时证据采集、逐条更新用例结果，以及最终结论提交。

这种方式具有较强的动态处理能力，但存在两个问题：

1. Agent 在每个操作后都可能需要重新推理，模型与工具之间往返次数较多。
2. 测试证据缺少明确分层，结构化信息、几何信息和截图没有根据用例风险进行差异化使用。

本方案不以单纯缩短耗时为目标。测试首先必须准确、可复现、可解释；只有在不降低证据质量的前提下，才优化执行速度。

## 2. 设计目标

目标优先级如下：

1. 测试结论可信，避免错误地判定通过。
2. 测试失败时有足够证据定位原因。
3. 测试过程稳定、可复现，避免用例之间相互污染。
4. 在不减少必要检查的前提下降低模型推理和工具调用开销。
5. 控制截图上传范围，降低不必要的隐私风险与模型输入成本。

## 3. 核心原则

### 3.1 结构化信息不能完全替代截图

结构化信息适合验证确定性事实：

- 元素是否存在、可见、启用或禁用。
- 输入框的值是否正确。
- 文本、数量、DOM 属性和 ARIA 状态是否符合预期。
- URL 是否正确跳转。
- 请求是否成功。
- 是否出现 Console Error 或 Page Error。

截图适合验证视觉事实：

- 元素是否遮挡、溢出或被裁切。
- 标签是否异常换行。
- 元素之间是否正确对齐。
- 弹窗位置、层级、间距和视觉状态是否正确。
- Canvas、图片或其他缺少 DOM 语义的内容是否正确。

视觉用例即使结构化断言通过，也不能直接判定通过。

### 3.2 截图在关键状态即时采集

不能把所有截图统一延迟到用例执行结束。弹窗闪退、加载状态错位、短暂遮挡等问题可能只存在于操作后的特定时刻。

截图应在关键检查点立即采集并保存在本地：

- 操作前。
- 操作完成后。
- 弹窗、菜单或浮层展开后。
- 动画稳定后。
- 结构化断言失败时。
- Console、网络或页面错误出现时。

截图采集与截图上传需要分离。采集后默认只返回证据 ID；只有视觉断言或异常诊断需要时，才将对应图片交给模型分析。

### 3.3 确定性判断优先于模型猜测

点击、输入、等待、URL 检查、DOM 检查、接口状态和几何计算应尽量由确定性执行器完成。Agent 主要负责：

- 根据需求和代码改动生成测试计划。
- 处理执行器无法定位的元素或无法恢复的状态。
- 分析结构化证据之间的冲突。
- 分析必要的视觉截图。
- 复核失败原因并生成结论。

## 4. 测试计划模型

开发完成后，Agent 应在当前上下文仍然完整时生成结构化测试计划，而不是等用户点击“开始测试”后重新理解需求。

建议的数据结构如下：

```json
{
  "title": "评论详情悬浮后保持显示",
  "risk": "high",
  "mode": "hybrid",
  "preconditions": [
    "页面已打开聊天面板",
    "目标消息至少包含一条评论"
  ],
  "steps": [
    {
      "action": "hover",
      "target": { "text": "1条评论" }
    },
    {
      "action": "movePointer",
      "target": { "text": "节点信息" }
    }
  ],
  "assertions": [
    {
      "type": "visible",
      "target": { "text": "节点信息" }
    },
    {
      "type": "visual",
      "rule": "鼠标从标签移动到详情弹窗期间，弹窗保持显示且未被聊天面板裁切"
    }
  ],
  "checkpoints": [
    "before-hover",
    "after-hover",
    "pointer-enter-popover"
  ]
}
```

每个测试用例必须明确：

- 业务目标。
- 前置条件。
- 操作步骤。
- 结构化断言。
- 视觉断言。
- 证据检查点。
- 风险等级。
- 状态恢复策略。

## 5. 用例分类

### 5.1 Structural

纯结构化用例，例如表单提交、文本变化、URL 跳转和请求结果。

默认采集 DOM、ARIA、URL、网络与运行时错误。截图可以本地留存，但不需要默认发送给模型。

### 5.2 Visual

视觉用例，例如对齐、遮挡、溢出、层级、颜色和间距。

必须同时采集几何数据和截图，并由视觉分析确认结果。

### 5.3 Hybrid

同时包含业务行为和视觉结果的用例，例如点击评论标签后弹出详情，并且弹窗不能被聊天面板裁切。

必须先执行结构化断言，再执行几何检测和必要的截图分析。任一关键断言失败，都不能判定用例通过。

## 6. 分层证据体系

### 6.1 第一层：结构化证据

- DOM 与可访问性信息。
- 元素可见性和交互状态。
- 输入值、文本和数量。
- URL 和路由状态。
- 请求方法、地址和响应状态。
- Console Warning/Error 与 Page Error。

### 6.2 第二层：几何与布局证据

- `getBoundingClientRect()`。
- `scrollWidth`、`clientWidth`、`scrollHeight`、`clientHeight`。
- 元素是否超出视口或滚动容器。
- 元素交叠面积。
- `overflow`、`position`、`z-index` 等关键计算样式。
- 点击目标是否位于可点击区域且未被其他元素覆盖。

### 6.3 第三层：视觉证据

以下情况需要分析截图：

- 用例本身包含视觉断言。
- 第一层或第二层断言失败。
- 不同层级的证据互相矛盾。
- 页面内容由 Canvas、图片或非语义化组件呈现。
- 用户明确要求视觉验收。

## 7. 截图证据管理

截图应先存放在 Chrome 扩展或 Agent 本地，不直接作为每次工具调用的模型图片输入。

建议的索引结构：

```json
{
  "screenshotId": "shot-123",
  "verificationId": "verification-456",
  "caseId": "comment-hover",
  "stepId": "pointer-enter-popover",
  "checkpoint": "after-action",
  "timestamp": 1788492345000,
  "pageUrl": "http://127.0.0.1:5173/",
  "domSnapshotId": "dom-789",
  "reason": "记录鼠标进入评论详情后的视觉状态"
}
```

截图生命周期建议限制在单次测试运行内。测试完成后，可保留失败用例证据，清理成功用例的临时图片；具体保留策略应允许后续配置。

## 8. 执行流程

推荐执行链路：

```text
Agent 生成结构化测试计划
→ 校验计划是否覆盖需求和高风险改动
→ 初始化干净且可验证的测试环境
→ 确定性执行器执行操作
→ 在关键检查点同步采集结构、几何和截图
→ 程序执行确定性断言
→ 视觉用例分析必要截图
→ 异常用例补充证据并按策略重试
→ 汇总每条业务断言
→ Agent 复核失败原因和证据一致性
→ 输出最终测试结论
```

### 8.1 操作后的组合快照

为减少重复调用，可以提供组合快照能力，一次返回：

- 当前 URL。
- 页面标题。
- 交互元素和可访问性摘要。
- 指定目标的几何信息。
- Console/Page Error 增量。
- 网络请求增量。
- 本地截图证据 ID。

组合快照只合并采集动作，不减少需要验证的证据。

### 8.2 条件等待

避免使用固定延迟作为主要同步方式，应等待明确条件：

- URL 匹配。
- 元素出现或消失。
- 元素状态改变。
- 请求完成。
- 页面进入稳定状态。

等待超时必须记录等待条件和实际页面状态，不能只返回笼统的超时错误。

## 9. 用例隔离和状态恢复

每个用例执行前应检查并恢复初始状态：

- 必要时刷新页面。
- 清理弹窗、菜单和焦点状态。
- 恢复或重新创建测试数据。
- 确认当前用户与权限。
- 等待关键请求完成。
- 记录执行前环境快照。

高风险、写操作或可能改变全局状态的用例应独立运行。只有只读且不存在状态依赖的断言才可以共享页面状态。

## 10. 失败分类与重试

测试失败应分类为：

- `code_defect`：有明确证据证明代码行为不符合预期。
- `environment`：服务、端口、浏览器或网络异常。
- `data`：测试数据或前置条件不满足。
- `permission`：登录、授权或角色权限不足。
- `flaky`：相同条件下执行结果不稳定。
- `insufficient_evidence`：证据不足，无法可靠判断。
- `unknown`：暂时无法归类。

不能把所有失败直接归因于代码。

推荐的重试规则：

- 明确的断言失败不盲目重试。
- 元素定位失败、等待超时或环境波动可以在恢复干净状态后重试一次。
- 重试时扩大证据采集范围。
- 两次结果不一致时标记为 `flaky`，不能判定通过。
- 重试次数必须受限，避免隐藏真实问题或无限延长测试时间。

## 11. 安全的性能优化

以下优化不应降低准确性：

1. 合并 DOM、ARIA、几何、Console 和网络摘要采集。
2. 点击或输入后直接返回操作后的组合快照。
3. 批量提交多条测试用例结果。
4. 在相关用例之间复用浏览器连接，同时对用例状态进行显式恢复。
5. 截图本地暂存，只将必要图片发送给模型。
6. 正常路径由确定性执行器完成，Agent 处理规划、异常和最终复核。
7. 使用条件等待代替固定延迟。
8. 对只读且相互独立的检查进行有限并行。

不建议为了提速采取以下措施：

- 全局取消截图。
- 只根据页面没有报错就判定通过。
- 跳过视觉需求的视觉验证。
- 为缩短时间而降低必要等待上限。
- 未恢复状态就连续执行相互影响的用例。
- 发生一次偶发成功就覆盖之前的失败结果。

## 12. 可观测性

优化前应先记录测试阶段耗时，避免依赖主观感受判断瓶颈。

每次测试建议记录：

- 测试计划生成耗时。
- Agent 首次响应耗时。
- 浏览器连接耗时。
- 每个浏览器操作耗时。
- 页面条件等待耗时。
- 结构化与几何快照耗时。
- 截图采集耗时。
- 截图上传与视觉分析耗时。
- Agent 推理总耗时。
- 工具调用次数和失败次数。
- 用例恢复与重试耗时。
- 测试总耗时。

测试结果详情中应能看到阶段耗时，但默认界面只展示关键瓶颈，避免干扰普通用户。

## 13. 分阶段实施

### 第一阶段：建立准确性基线和耗时基线

- 增加测试阶段计时和工具调用统计。
- 测试计划增加 `mode`、`risk`、`assertions` 和 `checkpoints`。
- 建立结构化、几何和截图三层证据模型。
- 为当前核心交互建立一组固定回归用例。

### 第二阶段：减少无价值的工具往返

- 增加组合快照接口。
- 操作后直接返回增量页面状态。
- 支持批量提交用例结果。
- 截图改为本地证据 ID，并提供按需读取接口。

### 第三阶段：引入确定性测试执行器

- 执行结构化测试计划。
- 支持语义化元素定位、条件等待和断言。
- 实现用例状态恢复与有限重试。
- Agent 只介入定位失败、证据冲突和异常诊断。

### 第四阶段：风险驱动优化

- 根据改动文件和需求自动识别高风险用例。
- 低风险结构化检查走快速路径。
- 高风险与视觉用例保持完整证据链。
- 基于历史数据识别不稳定用例和高耗时步骤。

## 14. 验收指标

准确性指标优先于性能指标：

- 核心回归用例无已知误判通过。
- 视觉用例必须包含几何和截图证据。
- 失败结论包含明确断言、实际结果和关联证据。
- 环境、数据和权限问题不会被错误归类为代码缺陷。
- 不稳定用例能够被识别，不能被偶发成功掩盖。
- 每条测试结论可以追溯到用例、步骤和证据。

在满足准确性指标后，再评估性能：

- 纯功能测试目标提升 30%～60%。
- 功能与视觉混合测试目标提升 20%～40%。
- 纯视觉测试目标提升 10%～25%。
- 减少模型工具往返次数，但不减少必要断言。
- 正常通过路径减少图片上传；异常路径允许增加诊断时间。

以上性能数字是目标范围，最终应以同一组回归用例改造前后的多次测量结果为准。

## 15. 建议的首个迭代范围

首个迭代建议只实现以下内容：

1. 测试全链路阶段计时。
2. 测试计划的用例分型和风险标记。
3. DOM、ARIA、几何、Console、网络的组合快照。
4. 关键检查点即时截图并返回本地证据 ID。
5. 视觉用例按需读取截图。
6. 测试结果展示断言、证据和阶段耗时。

这个范围能够先建立可信的证据体系和真实的性能基线，后续再决定确定性执行器需要覆盖哪些操作与断言，避免在缺少数据时过早设计复杂的测试 DSL。
